## D. Zmodyfikowane pliki

### `src/features/portal/api/portal-project.api.ts`
Całkowicie przepisany — z ~350 do 94 linii.

**Usunięto:** `validatePortalToken`, `portalGetProject`, `portalGetTimeline`, `portalGetApprovals`, `portalRespondApproval`, `portalGetMessages`, `portalSendMessage`, `portalMarkMessagesRead`

**Zostało:** tylko `createProjectPortalToken`, `revokeProjectPortalToken`, `listProjectPortalTokens` — obsługują `ProjectPortalCTA` (canonical invite flow).

### `src/features/portal/hooks/usePortalNotifications.ts`
Zastąpiony stubem — zwraca `{ notifications: [], unreadCount: 0, markAllRead: () => {}, dbUnreadCount: 0 }`.

Plik jest importowany przez `_auth.tsx` (layout operatora), który nie może być usunięty. Stary hook wykonywał `JOIN portal_messages ... client_tokens(client_name)` — po usunięciu tych tabel zapytanie by padło.

### `netlify/functions/client-identify.ts`
- Usunięto fallback lookup na `client_tokens` (blok `Promise.allSettled` + wtórna ścieżka `.from('client_tokens')`)
- Usunięto update `client_tokens.used_at` przez `Promise.allSettled`
- Pozostawiono: bezpośredni `project_portal_tokens.update` + upsert `client_accounts` + upsert `project_client_access` + wysyłka magic link

### `src/features/portal/model/project-portal.types.ts`
Usunięto:
- Interface `ProjectPortalSession`
- Interface `PortalSessionResponse`
- Wartość `'portal_token'` z unii `TimelineReferenceType`

## F. Model kanoniczny po Phase 4

```
Invite flow (aktywny):
  Operator → ProjectPortalCTA (email) → portal-token-create.ts
           → project_portal_tokens (token transparentny)
           → client-identify.ts → client_accounts + project_client_access
           → magic link → /client/project/:id

Portal klienta (aktywny):
  /client/project/:id  — auth-based (Supabase JWT + RLS)
  /client/dashboard    — auth-based

Sunset (aktywny):
  /portal/:token  → ekran "Ten link nie jest już aktywny"
  (brak walidacji, brak tworzenia sesji)
```

## H. Ryzyka i ograniczenia

### `project_portal_tokens` — pozostała na Phase 5
`ProjectPortalCTA` nadal tworzy rekord `project_portal_tokens` jako transparentny pośrednik invite flow. Dopóki `portal-token-create.ts` + `portal-revoke.ts` istnieją, tabela musi pozostać.

**Phase 5:** refaktorze `ProjectPortalCTA` tak, by bezpośrednio upsertował `project_client_access` z emailem klienta — bez pośrednictwa tokenów. Po tej zmianie można bezpiecznie:
- Usunąć tabelę `project_portal_tokens`
- Usunąć `netlify/functions/portal-token-create.ts`
- Usunąć `netlify/functions/portal-revoke.ts`
- Uprościć `client-identify.ts` do sygnatury `(company_id, project_id, email)`

### `usePortalNotifications` — stub, nie usunięcie
Hook jest importowany w `_auth.tsx` (layout root) — pliku, który zarządza routingiem i nie może być modyfikowany bez analizy całego drzewa tras. Stub zwraca puste dane i nie generuje obciążenia DB.
