# Dual Portal Architecture — Analiza i Plan Migracji

## Diagnozy Stanu Obecnego

### Portal A — Token-based `/portal/:token`

| Aspekt | Wartość |
|--------|---------|
| Trasa | `/portal/:token` (publiczna, bez logowania) |
| Komponent | `PortalProjectPage` (nowy) + fallback `PortalPage` (legacy) |
| Autentykacja | SHA-256 token → `project_portal_tokens` → `project_portal_sessions` |
| Transport danych | Netlify `portal-validate.ts` + `supabase.rpc()` z SECURITY DEFINER |
| Tabele | `project_portal_tokens`, `project_portal_sessions`, `project_messages`, `cost_approvals`, `project_timeline_events` |
| Zakładki | Aktualizacje · Wiadomości · Dokumenty (placeholder) · Akceptacje |
| Tożsamość klienta | opcjonalna (imię w localStorage, CTA do założenia konta) |
| Wysyłanie linku | ręcznie — operator kopiuje URL z tokenem |

### Portal B — Auth-based `/client/project/:id`

| Aspekt | Wartość |
|--------|---------|
| Trasa | `/client/project/:id` (wymaga zalogowania) |
| Komponent | `ClientProjectPage` |
| Autentykacja | Supabase auth — magic link z emaila zaproszenia |
| Transport danych | `client-portal.api.ts` → bezpośrednie zapytania Supabase z RLS |
| Tabele | te same: `project_messages`, `cost_approvals`, `project_timeline_events` |
| Zakładki | Temat/Wiadomości · Dokumenty · Akceptacje · Oś czasu |
| Tożsamość klienta | pełne konto Supabase (email, sesja JWT) |
| Wysyłanie linku | automatycznie — `client-identify.ts` Netlify → magic link → redirect z `project_id` |

### Diagram Przepływów

```
Stary przepływ (Portal A):
  Operator → kopiuje /portal/<token> → wysyła klientowi emailem ✉️ (ręcznie)
  Klient → otwiera link → Netlify portal-validate → session w localStorage
  Klient → używa portalu tokenowego (PortalProjectPage)

Nowy przepływ (Portal B):
  Operator → kliknie "Zaproś klienta" → client-identify.ts → magic link ✉️ (automatycznie)
  Klient → klika link → /auth/callback?project_id=... → zalogowany + redirect
  Klient → używa portalu auth (/client/project/:id)
```

## Obecny Stan Kodu

### Efektywne martwe gałęzie

**`PortalPage` (stary estimate portal)** jest w praktyce nieosiągalny:
- `portal/$token.tsx` zawsze renderuje `PortalProjectPage`, nie `PortalPage`
- `PortalPage` dostaje sterowanie TYLKO gdy `params.token` i `window.location.pathname` są oba puste — co normalnie nie zachodzi
- Renderuje dane z `client_tokens` (stara tabela) + `portal_messages` (stara tabela) przez `portal-get.js`
- Ta gałąź może zostać usunięta

**Stara tabela `client_tokens`** i Netlify `portal-get.js`:
- Jeszcze referencjonowane przez `portal.api.ts` i `usePortalData.ts`
- Nowe tokeny już nie są przez tę ścieżkę tworzone
- Bezpiecznie do usunięcia po wygaśnięciu starych tokenów

### Duplikacja — co czyta to samo dwukrotnie

Tabela | Portal A (RPC) | Portal B (RLS) | Akcje
---|---|---|---
`project_messages` | `portal_get_messages(session_id)` | `.from('project_messages').select(...)` | duplikacja odczytu
`cost_approvals` | `portal_get_approvals(session_id)` | `.from('cost_approvals').select(...)` | duplikacja odczytu
`project_timeline_events` | `portal_get_timeline(session_id)` | `.from('project_timeline_events').select(...)` | duplikacja odczytu

Dane są te same — różny mechanizm dostępu.

## Plan Migracji (fazy)

### Faza 0 — Bieżąca (wykonana ✅)
- Auth-based portal `/client/project/:id` działa w pełni
- Invite flow: `client-identify.ts` → magic link → `auth-callback.tsx` → redirect z `project_id`
- RLS policies scoped do `company_id` klienta (migr. 047)

### Faza 1 — Deprecacja nowych tokenów portalowych (wykonana ✅ v5.9)
**Cel:** Zaprzestać wystawiania nowych `project_portal_tokens` z UI.

**Zrealizowane zmiany (commit v5.9):**
1. `ProjectPortalCTA` — przepływ email-first: operator wypełnia email → token generowany transparentnie → `client-identify` wysyła magic link → `/client/project/:id`. Surowy URL `/portal/:token` nie jest już pokazywany.
2. `EstimateNextActions` — usunięto sekcję generowania tokenów z wyceny; panel kieruje do widoku Projektu.
3. `PortalLinksCard` — usunięto plik (brak konsumentów, używał starego `client_tokens`).
4. `PortalProjectPage` — banner dla klientów: "Dostęp przez link będzie wycofany — poproś firmę o zaproszenie emailowe."
5. Migracja 048 — `my_client_project_ids()` wyklucza `deleted_at IS NOT NULL`; widok `v_portal_token_activity` do monitoringu.

**Bez usuwania kodu** — istniejące sesje tokenowe nadal działają do wygaśnięcia.

### Faza 2 — Migracja aktywnych klientów (wykonana ✅ v5.9)
**Cel:** Wszyscy klienci z aktywnymi tokenami dostają nowe zaproszenie emailowe.

**Zrealizowane zmiany:**

1. **Migracja `049_portal_phase2.sql`** — dodano do `project_portal_tokens`:
   - `migrated_at timestamptz` — kiedy batch-migrator wysłał magic link
   - `migration_status text DEFAULT 'pending'` (`pending|migrated|no_email|skipped`)
   - Backfill: tokeny bez `client_email` dostają od razu `migration_status='no_email'`
   - Index częściowy na `migration_status = 'pending'` (szybkie query batch)
   - Widok `v_portal_migration_status` — kolumna `action`:
     - `ready` — pending + aktywny token + ma email → do migracji
     - `done` — zmigrowany
     - `no_email` — brak emaila, operator musi ręcznie zaprosi
     - `expired_token` — ma email ale token wygasł/unieważniony
     - `skipped` — poprzednia próba się nie powiodła

2. **Netlify function `portal-migrate-batch.ts`** — operator-triggered batch:
   - `POST /.netlify/functions/portal-migrate-batch`
   - `Authorization: Bearer <jwt>` + body `{ company_id, dry_run?, limit? }`
   - `dry_run=true` — raport bez wysyłki emaili (operator widzi plan)
   - Dla każdego Group A tokenu: upsert `client_accounts` → link `client_account_id` → upsert `project_client_access` → `admin.generateLink` (cichy, dla `auth_user_id`) → `signInWithOtp` (wysyłka) → `migration_status='migrated'`
   - Idempotentny: `already_done` (zmigrowane wcześniej) są pomijane, upserty nie tworzą duplikatów
   - Per-token error handling: błąd = `migration_status='skipped'`, kontynuacja
   - Odpowiedź: `{ migrated, skipped, already_done, no_email, errors[] }`
   - Email maskowany w `dry_run` response (bezpieczeństwo)

**Kryteria przejścia do Fazy 3:**
```sql
-- Oba warunki muszą być spełnione przez minimum 30 dni:
SELECT COUNT(*) = 0 FROM v_portal_migration_status WHERE action = 'ready';
SELECT COUNT(*) = 0 FROM v_portal_token_activity  WHERE last_seen_at > NOW() - INTERVAL '30 days';
```

## Ryzyko i Uwagi

| Ryzyko | Mitigacja |
|--------|-----------|
| Klient ma zapisany stary link i go używa | Banner na `/portal/:token` z instrukcją |
| Token wygasa w środku pracy klienta | `usePortalSession` ma auto-renewal co 5 min → bezpieczne |
| Klient nie może się zalogować emailem | Operator może resendować magic link z UI |
| RLS policy blokuje po migracji | Testy w Faza 1 na stadiowym Supabase |

## Rekomendacja

**Docelowa architektura (po Fazie 3):**
- Jedyny kanał klienta: `/client/project/:id` (auth-based, Supabase JWT)
- Jedyna metoda zaproszenia: magic link przez `client-identify.ts`
- `/portal/:token` nadal działa dla `project_portal_tokens` (aktualne linki) ale nie tworzy się nowych
- `PortalPage` (estimate portal) usunięty

**Korzyści po konsolidacji:**
- Jeden model danych dostępu (RLS, nie SECURITY DEFINER)
- Klient ma prawdziwe konto — może zobaczyć historię, wiele projektów
- Bezpieczniejsze (JWT > localStorage session)
- Mniej kodu do utrzymania (~500 linii usunięte)
