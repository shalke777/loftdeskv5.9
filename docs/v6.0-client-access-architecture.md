## CZĘŚĆ I — DIAGNOZA: Dlaczego checklista na Tablicy wisi

### Znalezione błędy (naprawione w tym commicie)

#### Bug 1: `portal: false` hardcoded w Supabase mode
**Plik:** `src/features/onboarding/hooks/useOnboardingProgress.ts`

```ts
// BYŁO (linia ~93)
portal: false, // can't check portal status cheaply here; skip

// JEST PO NAPRAWIE
portal: portalTokens.some((t) => t.active),
```

Krok „Uruchom portal klienta" nigdy nie mógł się zaznaczyć jako ukończony w trybie Supabase,
bo był na stałe ustawiony na `false`. W trybie demo działało poprawnie (przez `demoDb`),
stąd problem ujawniał się tylko po wdrożeniu.

#### Bug 2: Brak `invalidateQueries(['onboarding-progress'])` w mutacjach

Query key `['onboarding-progress', companyId]` **nie był nigdzie invalidowany** po żadnej operacji
zapisu. Oznacza to że po:
- dodaniu klienta
- stworzeniu projektu / kosztorysu
- aktywowaniu portalu
- zapisaniu profilu firmy

...checklista mogła się odświeżyć najpóźniej **po 30 sekundach** (poprzedni `staleTime`)
albo przy przeładowaniu strony.

**Naprawione przez dodanie `invalidateQueries(['onboarding-progress', companyId])` do:**
| Hook | Mutacja |
|---|---|
| `useClients.ts` | `useCreateClient` |
| `useProjects.ts` | `useCreateProject`, `useCreateProjectFromEstimate` |
| `useEstimates.ts` | `useCreateEstimate` |
| `usePortalData.ts` | `useCreatePortalToken` |
| `useSettings.ts` | `useUpdateCompanyProfile` |

#### Bug 3: `staleTime: 30_000` — zbyt wysoki

Zmniejszony do `5_000` ms. Mniejszy czas oznacza że zmiana widoczna jest niemal natychmiast
po nawigacji między stronami, nawet bez jawnego invalidate.

## CZĘŚĆ II — ARCHITEKTURA „ONE APP / TWO ROLES"

### Cel

Jedna aplikacja PWA. Jedno repo. Dwa shell UI zależne od roli:
- **Wykonawca** (`owner | admin | manager | worker | accountant`) — pełny system, bez zmian
- **Klient** (`client`) — lekki widok: swoje projekty, dokumenty, chat, akceptacje

## 1. Model danych — minimalne rozszerzenie

Obecna baza ma tabele: `companies`, `company_members`, `clients`, `projects`, `cost_estimates`,
`invoices`, `contracts`, `client_tokens`, `portal_messages`.

Potrzebne **nowe / rozszerzone tabele** (3 migracje):

### Migracja A: `client_accounts`

```sql
-- Konta klientów — oddzielne od company_members wykonawcy
create table if not exists public.client_accounts (
  id            uuid primary key default gen_random_uuid(),
  company_id    uuid not null references public.companies(id) on delete cascade,
  auth_user_id  uuid references auth.users(id) on delete set null,
  email         text not null,
  full_name     text,
  phone         text,
  created_at    timestamptz not null default now(),
  unique (company_id, email)
);

-- Klient jest powiązany z rekordami w tabeli clients przez email
-- Opcjonalnie: FK do clients(id) jeśli chcemy twardego powiązania
alter table public.client_accounts add column if not exists
  client_record_id uuid references public.clients(id) on delete set null;
```

### Migracja B: `project_client_access`

```sql
-- Które projekty widzi dany client_account
create table if not exists public.project_client_access (
  id               uuid primary key default gen_random_uuid(),
  project_id       uuid not null references public.projects(id) on delete cascade,
  client_account_id uuid not null references public.client_accounts(id) on delete cascade,
  granted_by       uuid references auth.users(id),
  granted_at       timestamptz not null default now(),
  unique (project_id, client_account_id)
);
```

### Migracja C: rozszerzenie `client_tokens`

```sql
-- Połącz istniejące tokeny z client_accounts (po przyjęciu zaproszenia)
alter table public.client_tokens
  add column if not exists client_account_id uuid references public.client_accounts(id) on delete set null,
  add column if not exists project_id uuid references public.projects(id) on delete set null;
```

Istniejąca tabela `client_tokens` to już de facto zaproszenie do portalu. Wystarczy ją rozszerzyć
zamiast tworzyć nowy system tokenów.

## 2. Model auth / access

### Role

```
auth.users (Supabase auth)
  └─ company_members (rola: owner|admin|manager|worker|accountant)  → wykonawca
  └─ client_accounts (rola: client)                                  → klient
```

W JWT Supabase dodajemy `app_role` jako custom claim lub odczytujemy z tabel:

```sql
create or replace function public.my_app_role()
returns text language sql security definer stable as $$
  select coalesce(
    (select 'client' from public.client_accounts where auth_user_id = auth.uid() limit 1),
    (select role  from public.company_members   where user_id      = auth.uid() limit 1),
    'anonymous'
  )
$$;
```

### RLS dla klientów

Zasada: klient widzi projekty, dokumenty i wiadomości **tylko przez `project_client_access`**.

```sql
-- Projekty: klient widzi swoje
create policy proj_client_select on public.projects for select
  using (
    id in (
      select pca.project_id
      from public.project_client_access pca
      join public.client_accounts ca on ca.id = pca.client_account_id
      where ca.auth_user_id = auth.uid()
    )
  );

-- Kosztorysy: klient widzi kosztorysy swoich projektów
create policy est_client_select on public.cost_estimates for select
  using (
    project_id in (
      select pca.project_id
      from public.project_client_access pca
      join public.client_accounts ca on ca.id = pca.client_account_id
      where ca.auth_user_id = auth.uid()
    )
  );

-- Faktury, umowy — analogicznie do cost_estimates
-- Koszty wewnętrzne: NIE dodajemy polityki dla klienta → brak dostępu
-- Expense_invoices: NIE dodajemy → brak dostępu
```

## 3. Flow klienta — od linku do stałego konta

```
1. WYKONAWCA
   └─ tworzy projekt + wycenę
   └─ generuje link portalu (istniejący mechanizm client_tokens)
   └─ wysyła link klientowi

2. KLIENT OTWIERA LINK (/portal/:token)
   └─ widzi wycenę, status projektu (istniejący portal — BEZ zmian)
   └─ może pisać w chacie, akceptować/odrzucać

3. KLIENT CHCE ZAINSTALOWAĆ APLIKACJĘ
   └─ prompt: "Zainstaluj LoftDesk Client"
   └─ pojawia się po 30s lub po akcji (akceptacji / wiadomości)

4. KLIENT WPISUJE EMAIL (identyfikacja)
   Netlify Function: POST /api/client/identify
   Body: { token: string, email: string, full_name?: string }
   
   Logika:
   a) Waliduj token (client_tokens.active = true)
   b) Znajdź lub utwórz client_accounts (company_id, email)
   c) Połącz token z client_account_id
   d) Stwórz wpis project_client_access dla projektu tokenowego
   e) Wyślij magic link przez Supabase Auth (supabase.auth.signInWithOtp)

5. KLIENT KLIKA MAGIC LINK W MAILU
   └─ Supabase tworzy/loguje konto w auth.users
   └─ Trigger DB: upsert client_accounts.auth_user_id = auth.uid()
   └─ Redirect do /client/dashboard

6. KLIENT MA STAŁE KONTO
   └─ Loguje się wpisując email → magic link
   └─ Widzi wszystkie swoje projekty (przez project_client_access)
   └─ Może wrócić bez linku
```

### Netlify Function: `client-identify`

```ts
// netlify/functions/client-identify.ts
export default async function handler(req: Request) {
  const { token, email, fullName } = await req.json()
  
  // 1. Waliduj token
  const { data: tokenRow } = await supabaseAdmin
    .from('client_tokens').select('id, company_id, project_id').eq('token', token).eq('active', true).maybeSingle()
  if (!tokenRow) return new Response('Invalid token', { status: 400 })
  
  // 2. Utwórz lub znajdź client_account
  const { data: account } = await supabaseAdmin
    .from('client_accounts').upsert({ company_id: tokenRow.company_id, email: email.toLowerCase(), full_name: fullName }, { onConflict: 'company_id,email' }).select().single()
  
  // 3. Podlinkuj token do konta
  await supabaseAdmin.from('client_tokens').update({ client_account_id: account.id }).eq('id', tokenRow.id)
  
  // 4. Nadaj dostęp do projektu (jeśli token ma project_id)
  if (tokenRow.project_id) {
    await supabaseAdmin.from('project_client_access').upsert(
      { project_id: tokenRow.project_id, client_account_id: account.id },
      { onConflict: 'project_id,client_account_id' }
    )
  }
  
  // 5. Wyślij magic link
  await supabaseAdmin.auth.admin.generateLink({ type: 'magiclink', email, options: { redirectTo: `${BASE_URL}/auth/callback?mode=client` } })
  
  return new Response(JSON.stringify({ ok: true }), { status: 200 })
}
```

## 4. Shell UI dla klienta

### Routing

```
/client                → ClientShell (layout)
  /client/dashboard    → Moje projekty (lista)
  /client/project/:id  → Projekt: dokumenty + chat + akceptacje + oś czasu
  /client/profile      → Dane kontaktowe klienta
```

Nowe trasy dodajemy obok istniejących w `router.tsx`:

```ts
const clientShellRoute = createRoute({ getParentRoute: () => authLayoutRoute, id: '_client', component: ClientShell })
const clientDashboardRoute = createRoute({ getParentRoute: () => clientShellRoute, path: 'client/dashboard', component: ClientDashboardPage })
const clientProjectRoute  = createRoute({ getParentRoute: () => clientShellRoute, path: 'client/project/$id', component: ClientProjectPage })
const clientProfileRoute  = createRoute({ getParentRoute: () => clientShellRoute, path: 'client/profile', component: ClientProfilePage })
```

### Redirect po zalogowaniu

W `AuthLayout` (lub `resolveSupabaseSession`):

```ts
// Jeśli user.role === 'client' → redirect do /client/dashboard
// Jeśli user.role jest wykonawczy → redirect do /dashboard (bez zmian)
```

### `ClientShell` — minimalistyczny layout

```tsx
function ClientShell() {
  return (
    <div className="client-shell">
      <ClientTopbar />       {/* Logo + email klienta + wyloguj */}
      <ClientNav />          {/* Projekty | Chat | Profil */}
      <main><Outlet /></main>
    </div>
  )
}
```

`ClientNav` ma **tylko**:
- Moje projekty
- Chat (suma nieprzeczytanych)
- Profil

**NIE MA** linków do: Ustawień, Faktur wewnętrznych, KSeF, Kosztów, Raportów, Admin.

### `ClientDashboardPage`

Lista projektów z `project_client_access`:
- Nazwa projektu
- Status (prostymi словami: „W toku", „Zakończony")
- Liczba nieprzeczytanych wiadomości
- Ostatnia aktualizacja

### `ClientProjectPage`

Widok projektu: zakładki **Dokumenty | Chat | Akceptacje | Oś czasu**

- **Dokumenty**: wyceny, umowy, faktury, zdjęcia z `project_photo_docs` — tylko read-only
- **Chat**: istniejący `ThreadView` / `MessageComposer` — klient może pisać
- **Akceptacje**: `PortalApprovalsTab` (istniejący) — adaptor do client mode
- **Oś czasu**: `ProjectTimeline` (istniejący)

Wszystkie zakładki to **reuse istniejących komponentów** z ograniczonym propsem `readOnly` lub
po prostu brakiem przycisków edycji.

## 5. PWA / instalacja

### Kiedy pokazać prompt

Nie na wejściu linkiem. Prompt wyskakuje gdy:
- Klient wykonał akcję (wysłał wiadomość, zaakceptował dokument) **AND**
- `beforeinstallprompt` event był zarejestrowany **AND**
- `localStorage.getItem('pwa-install-dismissed')` jest null

```tsx
// W ClientProjectPage lub ClientShell
useEffect(() => {
  const handler = (e: BeforeInstallPromptEvent) => {
    e.preventDefault()
    setInstallPromptEvent(e)
  }
  window.addEventListener('beforeinstallprompt', handler as any)
  return () => window.removeEventListener('beforeinstallprompt', handler as any)
}, [])
```

Banner: „Zainstaluj aplikację, żeby wracać bez linku" z przyciskami Zainstaluj / Nie teraz.
Po „Nie teraz" → `localStorage.setItem('pwa-install-dismissed', '1')`.

### Manifest — odróżnienie trybu

W `manifest.webmanifest` już mamy `start_url: "/"`. Klient po zalogowaniu ma `start_url`
ustawiony na `/client/dashboard`.

Można dodać drugi manifest specyficzny dla klienta (dynamicznie przez meta tag) lub
obsługiwać w `sw.js` przez URL scope. Najprostsze: tryb klienta startuje na `/client/dashboard`
automatycznie przez redirect po zalogowaniu.

## 7. Ryzyka i co trzeba pilnować

### RLS — najważniejsze

| Ryzyko | Mitygacja |
|---|---|
| Klient może zobaczyć dane innego klienta | RLS na `project_client_access.client_account_id = auth.uid()` — każda tabela |
| Klient może czytać `expense_invoices` (koszty wewnętrzne) | Brak polityki dla `client` na `expense_invoices` → domyślny brak dostępu |
| Marże w `cost_estimates` | Pole `internal_margin` nie iść przez portal API — filtrować w API/View |
| Notatki wewnętrzne | `projects.internal_notes` — nie serwować klientowi |
| Klient może wykonywać zapisy (INSERT/UPDATE) | Tylko `portal_messages` SELECT+INSERT, `client_accounts` UPDATE własnego rekordu |

### Auth — ryzyka

| Ryzyko | Mitygacja |
|---|---|
| Magic link przechwycony | Expiry 15 minut, single-use, HTTPS |
| Token portalu wycieknie email wykonawcy | `client-identify` nie zwraca danych o wykonawcy |
| Klient próbuje GET `/dashboard` (wykonawca) | `AuthLayout` sprawdza rolę i redirectuje do `/client/dashboard` |
| Klient w demo mode ma dostęp do wszystkiego | Demo mode używa `isDemoMode` guard — oddzielny demo klient |

### Widoczność dokumentów

Faktura, umowa i kosztorys mają dane wewnętrzne (np. marża, koszty robocizny bez VAT publicznego).
Przed udostępnieniem klientowi w `ClientProjectPage`:
- kosztorys: ukryj kolumnę `internal_cost`, `margin`
- faktura: pełna (klient ją dostaje w realu, więc OK)
- umowa: pełna (klient ją podpisuje)
- koszty (`expense_invoices`): całkowity brak dostępu

### Jedno źródło prawdy dla dostępu

`project_client_access` to master table. Nie tworzyć alternatywnych ścieżek dostępu
(np. przez `client_tokens.active`). Token to tylko zaproszenie — po aktywacji dostęp
pochodzi z `project_client_access`.

## 8. Co NIE wymaga zmian

- Router wykonawcy — bez dotknięcia
- Istniejący portal `/portal/:token` — działa jak dotąd, jest de facto entry point
- Tabela `client_tokens` — rozszerzamy, nie przebudowujemy
- `company_members` — bez zmian
- Cały system faktur / kosztorysów / projektów wykonawcy — bez zmian
- PWA manifest i sw.js — jeden plik, klient i wykonawca w tej samej apce
